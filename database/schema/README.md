# Database schema baseline

EIAAW Workforce keeps two schema dumps:

- `mysql-schema.sql` — historical Claritas portal schema (MySQL). Generated via `php artisan schema:dump --database=mysql`. Used as the input to the Postgres translator. **Do not delete** — it is the source-of-truth for the historical Claritas schema and the input to any re-translation.
- `pgsql-schema.sql` — Postgres-native baseline for the EIAAW Workforce SaaS deployment. Generated by `translate_mysql_to_pgsql.py`. **Loaded automatically** by `php artisan migrate` on a fresh Postgres database.

## How Laravel uses these on Postgres

When `DB_CONNECTION=pgsql` and `php artisan migrate` runs against an empty database:

1. Laravel detects `database/schema/pgsql-schema.sql` and loads it via `psql --file=...`. This creates all 88 historical tables AND populates the `migrations` table with all 80 historical migration entries marked as already-ran.
2. Laravel then runs only NEW migrations (anything dated after the dump's last entry, `2026_04_14_200000`).
3. The first new migration to run is `2026_05_01_000001_create_tenants_tables` (the SaaS foundation).

This means **you never run the 78 MySQL-only legacy migration files on Postgres** — they're treated as historical artifacts that produced the schema dump.

## Re-translating after a schema change

When you add new migrations on the MySQL Claritas side and want to bring them across to Postgres:

```bash
# 1. From the Claritas-MySQL machine: regenerate the MySQL dump
php artisan schema:dump --database=mysql

# 2. Run the translator
cd database/schema
python translate_mysql_to_pgsql.py
```

The translator is idempotent and produces the same output for the same input.

## Translation rules in summary

| MySQL                            | Postgres                                                            |
|----------------------------------|---------------------------------------------------------------------|
| `tinyint(1)` + `DEFAULT '0'/'1'` | `boolean` + `DEFAULT false/true`                                    |
| `int unsigned` / `bigint unsigned` | `integer` / `bigint` (no unsigned in PG; high bit not used by Laravel) |
| `enum('a','b','c')`              | `varchar(255)` + `CONSTRAINT x_check CHECK (col IN (...))`          |
| `json`                           | `jsonb`                                                             |
| `text COLLATE utf8mb4_unicode_ci`| `text` (cluster encoding handles unicode)                            |
| `datetime` / `timestamp`         | `timestamp(0)`                                                      |
| `KEY x (a, b)` after PRIMARY KEY | `CREATE INDEX x ON t (a, b);` after the table                       |
| `UNIQUE KEY x (a)`               | `CREATE UNIQUE INDEX x ON t (a);` after the table                   |
| `AUTO_INCREMENT`                 | `GENERATED BY DEFAULT AS IDENTITY` + sequence resync                |
| `ENGINE=InnoDB ... CHARSET=...`  | stripped                                                            |

## Limitations

The translator was written to handle the patterns ACTUALLY present in this codebase. It does NOT handle:

- `FULLTEXT` indexes (none in this schema)
- `SPATIAL` indexes (none)
- `GENERATED` columns (none)
- `MODIFY COLUMN` ALTER statements (these only appear in migration files, never in schema dumps)

If the schema grows new constructs, the translator will need updates. Run a smoke `psql -f pgsql-schema.sql` against a fresh empty Postgres database — any error means the translator missed a pattern.
